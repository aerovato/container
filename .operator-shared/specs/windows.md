# Windows

`container` runs natively on Windows (win32 + Docker Desktop) alongside Linux, macOS, and WSL. All OS-dependent logic is isolated in `src/platform/`, and an ESLint rule forbids `os`/`child_process`/`fs` imports and `process.platform`/`process.arch` access outside that module.

## Platform Abstraction

`src/platform/` is the only host-aware code; the rest of the codebase consumes its primitives plus the injected `ContainerClient`/`Executor`.

- `os.ts`: `Platform` enum and `isWindows()`/`isLinux()`/`isMacos()` predicates.
- `paths.ts`: host path constants, home expansion, project canonicalization, bind-mount construction.
- `fs.ts`: filesystem wrapper whose permission modes no-op on Windows.
- `shell.ts`: `Executor`, `commandExists` (`where` vs `which`), runtime availability/default detection.

## Path Handling

Project paths are canonicalized before deriving a container name. A native Windows drive-letter path (`C:\Users\dev\project`) is rewritten to its WSL mount form (`/mnt/c/Users/dev/project`), so the same project resolves to one container whether invoked from native Windows or WSL. Drive letters are case-normalized. This canonical form is used only for hashing the name, never as a filesystem path.

Bind-mount sources are normalized on Windows: backslashes convert to forward slashes (`C:\Users\...` → `C:/Users/...`), the form Docker Desktop accepts.

## Runtime Detection

When both Docker and Podman are available, `getDefaultRuntime` prefers Docker on Windows and macOS, and Podman on Linux.

## Permission Modes

`secureMkdir`/`secureWriteFile` apply restrictive Unix modes on POSIX. On Windows, modes are skipped (`mkdirSync` without `mode`, `chmodSync` not called); Windows ACLs govern permissions.

## Session Counting

`attachedSessionCount` counts `bash` processes via `docker top`. The output is generated by the Linux daemon (the container's process namespace), so it is identical regardless of the client host OS.

## Windows Safety Net

On Windows, `SIGHUP`/`SIGTERM` are not delivered by the OS, so abnormal terminal-close cleanup relies on the orphan sweep (`stopOrphanedContainers`), which runs on every CLI startup and stops managed containers idle beyond 5 minutes.

## Caveats

- Tool and harness `host` config paths are POSIX-tilde oriented (`~/.config/...`). `expandHomePath` resolves them against the Windows home, so migration succeeds where the path matches; where a tool stores config elsewhere (e.g. under `%APPDATA%`), that config is silently skipped. The container still functions; only the host config copy is affected.
- UNC paths (`\\server\share\...`) are not handled explicitly.

## Known Limitation

Dev build scripts use POSIX-only commands (`rm`, `chmod`, `bash`) in `package.json`. This does not affect installed consumers; it only affects building from a source clone on a Windows machine.
